# Процесс CarPlay

Держит сеанс с донглом Carlinkit, показывает картинку, играет звук и слушает
команды по локальному сокету. **Решений не принимает.** Какую кнопку куда,
показывать или прятать — дело автомата в [tools/agent/](../tools/agent/),
который покрыт тестами. Здесь только исполнение.

Написано и проверено на живом донгле 30.09.2026.

## Текущий аудиотракт: прямой PCM через ALSA

С 04.10.2026 собственные ресемплинг, коррекция скорости, стартовый запас 0.5 с,
подмешивание тишины и обрезка очереди удалены. Данные идут в установленный
`aplay`; частоту преобразует ALSA `plug`, потоки смешивает `dmix`. Новых
зависимостей нет. При единичной громкости PCM не изменяется побайтно.
Единственная обработка отсчётов — команды громкости/плавного приглушения
CarPlay; физический Headphone остаётся 124.

OUTPUT_STOP закрывает stdin: `aplay` доигрывает хвост, включая неполный период.
При смене формата прежний процесс также доигрывает, новый получает новый PCM.
Нет стартового таймера; задержка ALSA и донгла остаётся. Параметры ALSA пока
сохранены прежними, чтобы не менять одновременно несколько частей тракта.

Стандартная очередь Node Writable ограничена проверкой: более 4 с PCM означает
ошибку выхода с остановкой потока и паузой повторного запуска 3 с. Это аварийный
предел памяти, не целевая задержка. Максимум четыре процесса с учётом хвостов;
на завершение дано 15 с. При длительном дрейфе часов возможен такой отказ —
теперь он явно виден в журнале, вместо скрытого выбрасывания/ускорения данных.

`--zhurnal-ocheredi` оставлен совместимым со старым drop-in, но больше не пишет
подробный журнал: очереди ресемплера нет. Раз в 5 с журнал показывает объём stdin
и входной поток. Старый файл журнала не удаляется.

`npm test` проверяет все поддержанные форматы, побайтную передачу начала речи,
медленного получателя, EOF, смену формата, команды громкости и ограничение памяти.
Отдельно на машине нужно проверить музыку → WhatsApp → музыку и навигацию.
Автоматический запуск микрофона внутри `node-carplay` не менялся; ранее замеченная
смена аппаратной частоты после речи остаётся отдельным предметом диагностики.
Ниже сохранена история прежних вариантов; она не описывает текущий алгоритм.

## Решение по аудио: основной вариант и план Б (04.10.2026)

По решению пользователя оставляем текущий прямой вывод через `aplay` и ALSA
основным вариантом. Headphone — 124. Продолжаем оценивать стабильность по
прослушиванию и диагностике; отсутствие всех пропусков пока не подтверждено.

План Б — вывод через `pw-play`/PipeWire по примеру
[pi-carplay RGreeneRI](https://github.com/RGreeneRI/pi-carplay/blob/953be9892fd3d715ab0d6e5a7659556ba2f9392b/src/main/audio/AudioOutput.ts).
Это резервное направление, не начатая миграция и не замена всего приложения.
К нему возвращаемся отдельным решением, если текущий тракт не удастся сделать
стабильным. Перед переходом сравниваем один и тот же PCM на двух выходах,
проверяем музыку → речь → музыку, одновременную навигацию и микрофон.
Нужно учесть прежний сброс Headphone со стороны WirePlumber: сейчас WM8960
исключена из его управления правилом `51-carplay-wm8960.conf`.

## Запуск

```bash
cd ~/carplay
node index.js                            как есть
node index.js --bez-videa                только сокет, без окна
node index.js --zapis-videa /tmp/v.h264  писать поток в файл вместо показа
node index.js --zvuk carplay             ALSA PCM с микшером plug/dmix
node index.js --shirina 480 --vysota 280 другое разрешение у донгла
```

Запись в файл нужна, когда экрана под рукой нет: `ffprobe` потом скажет,
валидное ли это видео, а `ffmpeg` достанет кадр картинкой.

## Журнал

Пишется в `~/logi/carplay.log` с подрезкой по размеру. В journald смысла нет:
у пользовательских служб он тут не сохраняется.

Перехватываются и чужие ошибки — те, что библиотека печатает мимо нас, — иначе
в файле была бы половина картины. Отдельно ловятся падения дочерних процессов,
потому что снаружи они выглядят одинаково: просто ничего нет.

| В журнале | Что значит |
|---|---|
| `ffplay: завершился` / ошибка запуска | Картинки не будет. Обычно нет доступа к экрану |
| `aplay поток …: завершился` / ошибка запуска | Звука не будет. Занято устройство или не то имя |
| `не поднялся` | Рукопожатие с донглом не удалось, идёт следующая попытка |
| `телефона нет, прошу донгл поискать` | Телефон не подключился, отправлена команда сопряжения |

## Снимок экрана

Самый полезный приём отладки: посмотреть, что на самом деле на мониторе,
а не гадать по журналу.

```bash
DISPLAY=:0 XAUTHORITY=$HOME/.Xauthority \
  ffmpeg -v error -y -f x11grab -video_size 720x576 -i :0 -frames:v 1 /tmp/ekran.png
```

Так, например, сразу стало видно, что после одной из правок на экране висел
рабочий стол, хотя в журнале всё выглядело здоровым.

## Что умеет и чего не умеет управление

Проверено снимками экрана 30.09.2026.

| Хочу | Как |
|---|---|
| Следующий, предыдущий трек | Кнопки руля, стрелки монитора, либо крутилкой до `►►` |
| Пауза | Крутилкой до `❚❚` |
| Пропуск 15 секунд в подкасте | Работает: такие приложения рисуют свои кнопки, и они встают в фокус |
| **Перемотка внутри песни** | **Работает, крутилкой.** Порядок ниже |

Команд воспроизведения в протоколе ровно четыре: `play`, `pause`, `next`, `prev`.
Отдельной команды перемотки нет — проверено по коду библиотеки. Но она и не нужна:

1. Крутилкой встать на полосу прогресса — она подсветится широкой пилюлей.
2. **Нажать** крутилку: это вход в режим перемотки.
3. Крутить — примерно по 13 секунд на щелчок.
4. Нажать ещё раз, чтобы выйти.

**Важно, где именно.** На виджете плеера в рабочем столе CarPlay полоса в фокус
не встаёт и пальцем не тянется: выделение её проскакивает. Работает только на
**полном экране плеера**. Проверено снимками экрана 30.09.2026.

Отсюда же вывод про удержание стрелок монитора, которое штатно означает перемотку:
эмулировать его не нужно, и мы его игнорируем — у владельца есть крутилка.

## Звук: диагностика и исправления 02.10.2026

Симптом — треск и заикания, особенно на уведомлениях. **Объяснять всё дрейфом
кварцев было преждевременно:** повторная проверка выявила ошибки формата,
склейку разных потоков и повтор последнего отсчёта. Ниже описано текущее
поведение кода. Версия установлена на `bmwe39` 03.10.2026; результаты
проверки на устройстве приведены ниже.

### Что означают прежние замеры

В старом журнале были `177337 Б/с против 176400` (+0.531%) и стартовый всплеск
`315207 Б/с против 176400` (+78.7%). При устойчивой разнице 937 Б/с за минуту
набирается **56.2 КБ**, за час — 3.37 МБ. Прежние 530 КБ/мин были ошибкой.

Эти числа считались по общей очереди и предполагаемому формату 44100/стерео.
По ним нельзя отличить дрейф от другого формата, нескольких потоков или
пакетной подачи USB. Новые замеры считаются отдельно по каждому `audioType`
и сравниваются с его настоящей частотой и числом каналов.

В [asoundrc](../tools/asoundrc) сохранена действующая конфигурация Pi:
`/etc/asound.conf`, **44100 Гц, S32_LE, два канала** (сверено 04.10.2026).
`~/.asoundrc` на Pi отсутствует. Входной PCM может быть 44100, 48000 или
16000 Гц: ALSA `plug` приводит его к формату микшера. Первые три строки
выбирают карту 1 по умолчанию на этой установке; CarPlay использует именованную
`wm8960soundcard`. При переносе на другую плату номера карт нужно проверить.

### Что пробовали раньше

История наблюдений, а не доказательство единственной причины: эти опыты
проводились до исправления формата сообщений и разделения потоков.

| Подход | Наблюдение |
|---|---|
| Отдавать как приходит | В тишине буфер пустел, появлялись underrun и щелчки |
| Фиксированные порции по таймеру | Копилось отставание |
| Подача по часам с добавлением тишины | Недогрузок стало меньше, очередь росла |
| Выбрасывать по миллисекунде 50 раз в секунду | Треск на разрывах волны |
| Равномерно пропускать отдельные отсчёты | «Песочность» |
| Линейная интерполяция с коррекцией 2% и выше | Слышно изменение темпа |

### Как теперь устроено воспроизведение

- **Формат из `decodeTypeMap[message.decodeType]`.** В `AudioData` библиотеки
  нет полей `frequency` и `channel`. Раньше они всегда заменялись на 44100/2,
  даже у голоса 16000/1. Неизвестный тип и неполный PCM-кадр отбрасываются.
  `node-carplay` закреплён на проверенной версии 4.1.0.
- **Две независимые очереди по `audioType`.** Основной выход (1) и
  навигация/уведомления (2) идут в отдельные `aplay`. Микрофонный тип (3)
  не воспроизводится. Смешивание и преобразование форматов делает существующий
  `plug/dmix`; новой зависимости и собственного микшера нет.
- **Потребитель задаёт темп.** `Readable`/`Writable` прекращают подачу, пока
  запись в `aplay` не завершена. Вместо независимого таймера Node используется
  фактическая пропускная способность тракта. В очередях Node держатся небольшие
  порции по 20 мс; у ОС и ALSA есть дополнительные собственные буферы.
- **Начальное заполнение действительно ждёт данные.** Цель — 0.5 секунды PCM.
  Если звук короче, он начинает играть после 0.5 секунды ожидания либо после
  `OUTPUT_STOP`. При голодании следующий фрагмент снова проходит заполнение.
- **Интерполяция в обе стороны с сохранением дробной позиции.** Предел
  подстройки ±0.6% покрывает прежнее число +0.531%, но не гарантирует
  компенсацию любого расхождения или неслышимость. При окончании данных
  очередь очищается: последний отсчёт больше не повторяется каждые 20 мс.
  Начало и конец доступного фрагмента сглаживаются за 5 мс.
- **Память ограничена.** Если входная очередь превышает секунду, оставляется
  последние полсекунды по границе PCM-кадра. Обрезки считаются в журнале.
  Такая аварийная обрезка по-прежнему может быть слышна.
- **Управление отдельно от PCM.** Сообщения `volumeDuration` задают громкость
  указанного `audioType` с плавным переходом (длительность в секундах).
  Поле `volume` обычного PCM-пакета не трактуется как команда: в нём бывает 0
  при нормальном звуке. `OUTPUT_STOP` своего формата отмечает конец подачи,
  не уничтожая хвост. Остальные команды записываются в журнал; микрофонными
  командами по-прежнему занимается `CarplayNode`.
- **Смена формата и ошибки процессов изолированы.** Событие от старого
  `aplay` не закрывает новый. Ошибка запуска/трубы даёт паузу 3 секунды перед
  следующей попыткой. Отключение телефона/донгла очищает оба потока.

**Нужен ALSA-микшер.** По умолчанию используется `--zvuk carplay` из
[asoundrc](../tools/asoundrc). Можно указать другой PCM с поддержкой смешивания.
Прямые `hw:` и `plughw:` отклоняются: два потока и служба `zvuk-zhivoy`
не смогут одновременно открыть эксклюзивное устройство. Проводные наушники
при этом подключаются к физическому выходу той же платы.

На живом WM8960 запрос `--period-time=40000` фактически дал период 5513
кадров (125 мс). Запрос буфера 200 мс давал только два периода (250 мс)
и сопровождался underrun. Запрос увеличен до 500 мс: ALSA выделяет
доступные три периода, 16539 кадров (375 мс). Это аппаратная калибровка,
а не изменение входной очереди или предела коррекции.

Суммарная задержка **не равна ровно 0.5 с**: к входному запасу добавляются
очереди ОС и ALSA. На стенде нужно проверить задержку музыки, уведомлений и
голоса. В частности, при моно 16000 Гц одинаковое число байт в трубе означает
больше секунд. Два независимых проигрывателя не обеспечивают покадрового
выравнивания потоков. Если это окажется слышно, следующий шаг — единый
выходной PCM-тракт с общими часами, а не увеличение буфера.

### Запись сообщений для проверки дома

Сначала остановить службу, чтобы второй процесс не спорил с ней за USB и
сокет. Команды выполняются на Raspberry Pi от пользователя службы:

```bash
systemctl --user stop carplay.service
cd ~/carplay
node index.js --bez-videa --zapis-zvuka /tmp/carplay-audio.jsonl
# Включить музыку, вызвать несколько уведомлений, дождаться их окончания.
# Ctrl+C завершает запись.
systemctl --user start carplay.service
```

Запись содержит исходные сообщения до обработки: монотонное время `ms`,
`decodeType`, `audioType`, `command`, `volume`, `volumeDuration` и PCM в Base64.
Каждая строка — отдельный JSON. Файл создаётся с правами 0600 и **не
перезаписывается**, если уже существует; для следующего замера выбрать новое
имя. Это запись реального звука, поэтому не публиковать её без проверки.
Предел — 32 МиБ. Если диск не успевает, запись заканчивается раньше с
сообщением в журнале; воспроизведение продолжается. При штатной остановке
даётся до двух секунд на завершение записи.

Слушать через **проводные наушники на выходе звуковой платы**. Bluetooth
добавляет собственную обработку и буферизацию. В журнале раз в пять секунд
видны `звук audioType/decodeType`, входящий поток, номинал, очередь, обрезки
и опустошения. Опустошение также нормально в конце короткого звука; искать
нужно повторения во время непрерывной музыки.

Проверить: музыка не менее 10 минут; несколько коротких уведомлений во время
музыки и в тишине; пауза/возобновление; переход к Siri/звонку и обратно;
отключение телефона и USB с повторным подключением. Окончательную причину
прежнего дребезга и качество исправлений подтверждает этот замер, не тесты.

Контракт сверялся с [node-carplay 4.1.0](https://registry.npmjs.org/node-carplay/-/node-carplay-4.1.0.tgz).
Описание маршрутов и управляющих сообщений сопоставлено с
[исследованием протокола CPC200-CCPA](https://github.com/lvalen91/CPC200-CCPA_resources/blob/main/documentation/02_Protocol_Reference/audio_protocol.md).
Поведение конкретной прошивки всё равно проверяется записью.

## Остальные исправления проверки 02.10.2026

- USB: отключение фиксируется даже во время запуска; `failure` будит надзор
  без ожидания физического извлечения. Запуск ограничен 10 секундами,
  закрытие драйвера — двумя; просроченное ожидание снимается. После `failure`
  следующая попытка выполняет USB reset (не чаще раза в 30 секунд): на
  живом донгле повторное открытие и `clearHalt` не устранили `babble` на IN.
  При первом нормальном подключении сброс по-прежнему не выполняется. Поддерживаются
  оба USB ID из библиотеки, 1520 и 1521. После перезапуска хоста поступление
  видео или PCM также подтверждает подключение телефона: донгл не всегда
  повторяет `Plugged`. После отключения телефона возобновляется
  поиск. Старые сообщения и отложенные команды не действуют на новый сеанс.
- Видео: убран `nobuffer`, чтобы не выбрасывать пакеты начальной разведки;
  запрос опорного кадра каждые 5 секунд теперь принадлежит проигрывателю
  и не зависит от получения `Plugged`. Убран неограниченный `infbuf`.
  Ошибки запуска/трубы и завершение по сигналу обрабатываются;
  запоздалый `exit` старого `ffplay` не сбрасывает новый. При забитой трубе
  очередь не растёт бесконечно: поток заново ждёт SPS и запрашивает опорный
  кадр. Запись видео не перезаписывает существующий файл и прекращается,
  если диск не успевает.
- Сокет: `null`, массивы, некорректные числа и действия больше не приводят
  к падению или случайному касанию. Максимум 4096 байт на строку и 16 клиентов;
  слишком длинная строка и медленный получатель отключаются. Права — 0600,
  клиент должен работать от того же пользователя. При запуске проверяется
  живой слушатель: чужой файл и сокет работающего процесса не удаляются.
- Журнал: ротация действует во время работы, остаются текущий файл и `.1`
  по 5 МиБ. При ротации/медленном диске часть файловых строк пропускается;
  консольный вывод сохраняется. Это исключает неограниченное накопление
  файлового журнала в памяти.
- Параметры: проверяются размеры видео/экрана, FPS и интервал поиска.
  `StartLimitIntervalSec` перенесён в секцию `[Unit]` службы.

### Автоматическая проверка и установка

Из корня репозитория:

```bash
node --check carplay/index.js
node carplay/audio-check.cjs
# Либо: cd carplay && npm test
```

Один assert-based файл, без фреймворка и установки зависимостей, проверяет
форматы `decodeType`, раздельные потоки, моно/стерео, фазу интерполяции,
короткий звук и его конец, границы очереди, громкость, старые события процессов,
реальные Node-потоки с заблокированным получателем, видео, USB-ожидания,
настоящий Unix-сокет, запись PCM и ротацию журнала. Дочерние процессы и USB
заменены заглушками: это не проверка ALSA или физического донгла.

После копирования обновлённых файлов в `~/carplay` на Pi:

```bash
cd ~/carplay
npm install
npm test
cp carplay.service ~/.config/systemd/user/carplay.service
systemctl --user daemon-reload
systemctl --user restart carplay.service
```

Нужен PCM `carplay` с `plug/dmix` в `~/.asoundrc` либо `/etc/asound.conf`.
Не заменять действующую настройку примером из проекта без проверки частоты
и карты: на `bmwe39` уже используется системный микшер на 44100 Гц.

## Протокол на сокете

`/tmp/carplay.sock`, строки JSON, по одной на строку.

| Направление | Сообщение |
|---|---|
| нам | `{"cmd":"navigate","right":true,"steps":1}` |
| нам | `{"cmd":"select"}` `{"cmd":"back"}` `{"cmd":"home"}` |
| нам | `{"cmd":"next"}` `{"cmd":"prev"}` `{"cmd":"play"}` `{"cmd":"pause"}` |
| нам | `{"cmd":"touch","action":"down","x":0.5,"y":0.78}` |
| от нас | `{"event":"phone","connected":true}` |

`touch` — отладочный примитив: ткнуть в экран. Координаты **нормированные**,
от 0 до 1, поэтому не зависят от разрешения. Действия `down`, `move`, `up`;
из них складывается и перетаскивание. В машине касания не понадобятся —
там крутилка и кнопки, — но на стенде это единственный способ добраться
куда-то быстро. Им же управляет [mysh.py](../tools/mysh.py), превращающий
мышь в палец.

`back` **контекстный**, как на заводских головных устройствах: сначала отменяет
то, во что вы вошли, и только следующим нажатием уводит на уровень выше.
Проверено: первый `back` вышел из режима перемотки, второй — из плеера.

Состояние телефона отправляется каждому клиенту сразу при подключении, чтобы
ему не приходилось ждать следующего изменения.

## Грабли автозапуска и задержки

Обе найдены 30.09.2026, обе выглядели снаружи как «софт не работает».

**`graphical-session.target` на этой системе не активируется.** Служба была
повешена на неё по здравому рассуждению: процессу нужен графический сеанс.
Но на Raspberry Pi OS с lightdm эта цель не поднимается, хотя X работает и
пользователь залогинен. Служба остаётся `enabled` и после перезагрузки
не стартует. Лечится переводом на `default.target` плюс `enable-linger`.

**`ffplay` до первого кадра изучает поток.** По умолчанию он читает до пяти
мегабайт или пяти секунд, прежде чем показать хоть что-то. На нашем небольшом
потоке упор идёт в пять секунд, и это выглядит как «картинка появляется очень
поздно». Лечится ключами `-probesize 32768 -analyzeduration 0`.

Измерено после правки 30.09.2026: от запуска процесса до первого кадра
**434 мс**, из них 419 на подъём окна и 15 на приход видео. Было около пяти
секунд. Если когда-нибудь снова станет медленно — вот число для сравнения.

**Окно не убивается при отключении телефона.** Раньше оно создавалось заново на
каждое подключение, и в самый нужный момент тратилось время на его создание и
захват экрана. Хуже того: если к моменту отключения состояние уже считалось
«телефона нет», окно убивалось молча, без единой строки в журнале — снаружи это
выглядело как «подключил телефон, ничего не произошло». Теперь окно живёт,
пока жив сеанс с донглом: телефон ушёл — картинка замерла, вернулся — пошла
дальше.

**Код 123 это не ошибка.** Так `ffplay` завершается по нашему же сигналу.
Подписывать это ошибкой — значит потом искать поломку, которой нет; в журнале
теперь пишется «ffplay остановлен нами».

**Что осталось и не лечится с нашей стороны.** От подключения телефона к Wi-Fi
донгла до момента, когда донгл опознал CarPlay, проходит 2–3 секунды: это
проверка подлинности Apple внутри донгла. Сразу после неё видео идёт без
паузы. В машине это почти незаметно, потому что картинка попадает на монитор
только по команде платы, а команда даётся уже по готовности.

Заодно окно теперь создаётся сразу при установке сеанса, а не в момент
подключения телефона: создание окна и захват экрана занимают заметное время,
и тратить его в самый нужный момент незачем.

**Как понять, где теперь упирается.** В журнале есть две строки:
`телефон подключился` и `пошли кадры видео`. Пауза между ними — это донгл,
а не мы; всё, что после, — наша часть.

## Две вещи, из-за которых это не заводилось сразу

**Донгл перезагружается сам.** Если хост не начал с ним разговаривать, он через
несколько секунд уходит в сброс: в логе ядра видно отключение и подключение
примерно раз в тринадцать секунд. Поэтому мало открыть его один раз — надо
ловить каждое появление. Процесс подписан на события USB и стартует сразу за
подключением, а не по таймеру.

**Штатный `carplay.start()` не годится.** Он сначала сбрасывает устройство,
ждёт три секунды и ищет заново. Наш донгл в это время сбрасывается сам, два
сброса сталкиваются, и `reset()` падает с `LIBUSB_ERROR_NOT_FOUND`. Мы этот
шаг обходим: находим устройство через `webusb`, открываем и зовём
`dongleDriver.initialise()` и `dongleDriver.start()` напрямую. Сброс не нужен —
устройство и так только что перечислилось.

## Автозапуск

Запускать процесс «при подключении телефона» не нужно и невозможно: донгл виден
системе всё время, а телефон появляется и пропадает уже внутри работающего
сеанса. Поэтому служба живёт постоянно, а на подключение реагирует сама.

```bash
mkdir -p ~/.config/systemd/user
cp ~/carplay/carplay.service ~/.config/systemd/user/
systemctl --user daemon-reload
systemctl --user enable --now carplay.service
```

Служба **пользовательская**, а не системная: картинка рисуется в тот же X,
который выводится на композит. И ей обязательно нужны `DISPLAY` и `XAUTHORITY` —
они прописаны в юните. Без них всё выглядит работающим (звук идёт, сокет есть),
но картинки нет, потому что `ffplay` не знает, куда рисовать.

- **Показ на настоящем экране работает.** Композитный монитор подключён,

  возобновления по таймеру. Поведение сохранено как на Pi.
- Подробный журнал не ограничен по размеру и не обрабатывает `write(false)`:
  при медленном диске очередь записи может расти в памяти. Он пригоден для
  временной диагностики; для постоянного включения нужны ограничение объёма
  и прекращение записи при backpressure.
- `Before=carplay.service` задаёт порядок лишь при совместном запуске служб.
  Ожидание карты и `sleep 5` — эвристика, а не зависимость от системного
  `alsa-restore`. Проверка после физического отключения питания остаётся
  открытой; для гарантированного порядка потребуется системная служба,
  запускаемая после восстановления ALSA.

[Копия временного drop-in](carplay.service.d/zhurnal-ocheredi.conf) сохранена
из установленной конфигурации. Обычное копирование `carplay.service` его не
включает. На Pi он уже включён; здесь его состояние не менялось. После
проверки в поездках его можно выключить (перезапуск прервёт звук и экран):

```sh
rm ~/.config/systemd/user/carplay.service.d/zhurnal-ocheredi.conf
systemctl --user daemon-reload
systemctl --user restart carplay
```

Короткий успешный замер из предыдущей сессии не заменяет проверку в поездке.

### Пробная правка начала речи 04.10.2026 — отменена

При запуске голосового WhatsApp на телефоне пользователь слышит потерю начала
через CarPlay. В журнале Pi у моно 16 кГц обнаружены обрезки очереди;
принадлежность этих событий WhatsApp пока не подтверждена. Проверка старого
кода воспроизводит потерю первых 0.7 с при разовом поступлении 1.2 с PCM.

Для моно 8/16/24 кГц предел очереди увеличен с 1 до 4 секунд. Начальное
накопление остаётся 0.5 с; музыкальный стереопоток сохраняет прежний лимит.
Это ограниченная мера против пакетных всплесков, не гарантия сохранения
произвольно длинного сообщения: после превышения 4 с действует прежняя обрезка.
При накоплении очереди задержка речи может увеличиться. Если WhatsApp передаёт
стерео, эта мера на его очередь не влияет. Требуется проверка на устройстве.

Также таймер теперь ждёт остаток до 250 мс от последнего пакета, а нормальное
доигрывание после OUTPUT_STOP не увеличивает счётчик голоданий. Эти два пункта
ревью выше описывают прежнюю версию. Ограничения журнала и службы громкости
пока остаются. Тесты проверяют сохранность начала в одном и нескольких пакетах,
предел памяти, остаток таймера и штатное окончание.
